# Official protocol 767 registry generation

ZCraft builds its dynamic registries from the **official Minecraft Java 1.21.1
server JAR**, not a checked-in third-party `registries.json`.

## Build pipeline

```text
cargo build / check / test
    → build.rs checks a versioned, integrity-checked generated cache
    → cache missing/stale:
        obtain the pinned official bundler JAR
        verify byte count + Mojang SHA-1
        read the inner server JAR without executing it
        selectively extract registry JSON into a temporary directory
        project JSON to network data and encode NBT
        generate registries.rs + cache metadata
    → copy valid Rust constants into Cargo OUT_DIR
    → src/registry_data.rs includes the generated constants
```

No Java runtime or running Minecraft server is involved. EULA acceptance is
neither read nor changed by the build; normal ZCraft startup still requires it.

## Files and generated artifacts

| File | Responsibility |
| --- | --- |
| `build.rs` | Download policy, orchestration, Cargo rebuild tracking |
| `build_support/archive.rs` | Bounded, allowlisted nested-JAR extraction |
| `build_support/registry.rs` | JSON projection, NBT encoding, Rust generation |
| `build_support/cache.rs` | Pinned JAR verification, cache fingerprints, atomic writes |
| `src/registry_data.rs` | Runtime facade over generated packet bodies |
| `assets/protocol/767/NOTICE.md` | Official source and rights notice |

Default cache layout:

```text
target/zcraft-data/1.21.1/
├── server.jar                 # Retained only when automatically downloaded
└── <generator-source-hash>/
    ├── registries.rs          # Pre-encoded packet bodies as Rust byte constants
    └── manifest.json          # Version, JAR hash, generator hash, source hash
```

A generated cache is reused only when its metadata, generator fingerprint and
source checksum match. Changes to the generator invalidate its generated output
but can reuse the pinned JAR. Missing or corrupt output is regenerated; it is
never silently replaced with empty or third-party data. Files are atomically
published, so a failed download does not publish a partial JAR or source.

The build copies the generated source to `OUT_DIR/registries.rs`, and does not
write generated Rust into `src/` or execute downloaded code. Compilation embeds
all generated bytes, so deployed binaries need neither a JAR nor a registry JSON
file. The runtime still uses full registry payloads, with no known-pack elision.

## Downloads and offline builds

The official version metadata fixes the input to:

- Minecraft: `1.21.1` / protocol `767`.
- Size: `51,627,615` bytes.
- SHA-1: `59353fb40c36d304f2035d51e7d6e6baa98dc05c`.
- Download URL and source notice:
  [assets/protocol/767/NOTICE.md](../assets/protocol/767/NOTICE.md).

Downloads require HTTPS, reject redirects, impose connection/total timeouts and
a fixed byte limit, and are verified before ZIP processing. The build may use
the standard HTTPS proxy environment supported by reqwest.

| Environment variable | Meaning |
| --- | --- |
| `ZCRAFT_SERVER_JAR` | Local official **bundler** JAR, checked against the same size/hash when generation is needed |
| `ZCRAFT_DATA_CACHE` | Trusted writable cache root; default `<project>/target/zcraft-data` |
| `ZCRAFT_DATA_OFFLINE=1` | Forbid downloading data; use valid generated cache or verified local/cached JAR |

Examples:

```sh
# First build: missing data is downloaded automatically.
cargo build

# Generate without network from an existing official JAR.
ZCRAFT_SERVER_JAR=/path/to/server-1.21.1.jar \
ZCRAFT_DATA_OFFLINE=1 cargo build

# Reuse a prewarmed cache, including in CI.
ZCRAFT_DATA_CACHE=/path/to/trusted-cache \
ZCRAFT_DATA_OFFLINE=1 cargo build
```

A valid generated cache takes priority over the local-JAR override. The local
JAR is not copied into the cache; retain it if regeneration will be needed.
These environment variables affect the build, not `zcraft.toml`.

**Cargo's `--offline` only controls Cargo dependency fetching.** Set
`ZCRAFT_DATA_OFFLINE=1` as well to forbid this build script's data download.
Offline dependency builds also require the normal Cargo dependencies to have
been cached. Do not use an untrusted/shared writable cache: generated Rust is
compiled as code, and its checksum is an integrity check, not a signature.

## Registry and ID contract

| Registry (`minecraft:` prefix) | Entries |
| --- | ---: |
| `worldgen/biome` | 64 |
| `chat_type` | 7 |
| `trim_pattern` | 18 |
| `trim_material` | 10 |
| `wolf_variant` | 9 |
| `painting_variant` | 50 |
| `dimension_type` | 4 |
| `damage_type` | 47 |
| `banner_pattern` | 43 |
| `enchantment` | 42 |
| `jukebox_song` | 19 |

All 313 entries are sent. Entry position determines its network ID. Entries are
sorted lexically, except `minecraft:plains` is forced to biome ID **0** and
`minecraft:overworld` to dimension-type ID **0** to match the current world.

Generation validates overworld geometry: `min_y=-64`, `height=384`,
`logical_height=384`, `has_skylight=true`. An unexpected entry count, malformed
JSON, invalid filename or changed geometry fails the build.

## JSON → network NBT

Ordinary JSON does not carry NBT primitive widths. This version-specific
generator writes booleans as Byte, exact signed integers as Int/Long and decimal
numbers as Double. Minecraft codecs read numeric primitives through number
conversions. Lists must have a homogeneous NBT element type; mixed numeric lists
are promoted only if integer precision is preserved. Null, unsupported mixed
lists and excessive nesting/sizes fail instead of silently discarding data.
Strings use Java modified UTF-8 and the root is an anonymous Compound.

Biome JSON includes server world-generation fields that are not in the client
network codec. The generator keeps only precipitation, temperature, optional
temperature modifier, downfall and effects. The other ten registry payloads use
their data-pack field representations. This is deliberately pinned to 1.21.1:
upgrading requires checking the actual network codecs, not just changing a URL.

Packet bodies exclude their packet ID and frame length. Every entry has
`has_data=true`. They are generated once at build time, not parsed/encoded from
JSON on each server startup.

## Tags and validation limits

`tags_packet()` contains all 514 vanilla tags across 13 network-safe registries
(25,200 bytes). Definitions are extracted from the verified official JAR;
`build_support/tags.rs` resolves nested references, deduplicates members and
rejects cycles or missing required entries. Dynamic IDs follow the transmitted
registry order. Static IDs come from the checked-in official data-generator
report in `assets/protocol/767/static_registry_ids.json`. The 16 server-only
worldgen tags are intentionally not synchronized.

Normal builds still do not execute Java. Maintainers can reproduce the static
ID snapshot using `build_support/generate_static_registry_ids.py` with the
verified official JAR and Java 21. See the asset NOTICE for provenance.
Custom data packs and complete tag-dependent gameplay remain out of scope.

Normal tests cover NBT primitives/lists/modified UTF-8, deterministic output,
missing or malformed registries, ZIP path handling, size limits, cache
invalidation and all runtime registry packets.

To explicitly regenerate twice from a verified official JAR during tests:

```sh
ZCRAFT_TEST_SERVER_JAR=/path/to/server-1.21.1.jar \
  cargo test --test registry_codegen -- --nocapture
```

The independent protocol-client test documented in README checks registry wire
decoding, terrain/light decoding and continued Play connections. Actual vanilla
Java 1.21.1 graphical-client registry semantics and rendering still require
manual validation; a parser test is not a replacement for that.
